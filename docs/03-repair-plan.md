# 分阶段修复计划

目标分为两层：先恢复本机截图任务，再让官方 `sky.get_window_state` 原生窗口截图恢复。第二层当前仍未完成。

## 阶段 0：建立可回溯基线（已完成）

1. 读取原始文档、确认目录原先不是 Git 仓库。
2. 初始化 `main` 分支并创建本地提交 `2df52f4`，原文保持不变。
3. 将原文迁入 `docs/archive/`，以 SHA-256 确认内容一致。
4. 将证据、根因、操作说明和后续计划拆开，避免把历史推测当成本次结论。

## 阶段 1：恢复可见桌面截图（已实施、已验证）

交付：`tools/capture_screen.py`。

- 使用已存在的 Python 与 Pillow，不依赖新增 `mss`、SDK 或驻留服务。
- 支持虚拟桌面、指定显示器以及图像 / 屏幕坐标裁剪。
- 记录布局、原点、尺寸、时间、后端和 PNG 哈希。
- 检查桌面可访问性、每显示器 DPI 感知和截图期间的布局变化。
- 拒绝越界裁剪和覆盖已有输出；纯色结果提示复核。
- 将截图放在 Git 忽略目录，避免把桌面私人内容随提交传播。

已通过整屏、主屏和局部真实截图，以及负原点坐标测试。限制是只能读取实际可见像素；目标被遮挡、最小化或处于受保护内容场景时，不能保证内容完整。该阶段不提供与官方 `screenshotId` 等价的对象。

## 阶段 2：原生截图后端兼容修复（待官方可部署实现）

这是保留现有 LTSC 系统时的优先原生修复路线。

**第二轮实测修正：**已在本地尝试跳过可选的边框关闭操作；错误继续推进到 `FrameArrived timed out`。同包 Swift 后端也在截图时崩溃。两者均已回退，因此下面的能力判断只是必要的兼容修复点，不能被视为已经验证充分的解决方案。

1. 使用 [问题报告草稿](06-upstream-report.md) 向具有后端源码和发布权限的维护者提供最小复现；草稿尚未外发。
2. 在原生捕获层设置 `IsBorderRequired` 前，检查属性或对应接口是否存在。
3. 若缺失，保留系统默认边框并继续基本捕获；不要把可选的边框控制变成整次截图的硬依赖。
4. 只对确认属于该可选属性的缺失接口错误做兼容处理；设备丢失、窗口无效、权限拒绝等仍应报告。
5. 对其他可选 WGC 属性独立探测，不仅按一个硬编码 Windows 版本判断。
6. 由官方发布可验证的版本，再重启相关应用 / 会话加载新后端。

建议测试矩阵：

| 环境 | 验收要点 |
| --- | --- |
| 当前 19044 LTSC，属性缺失 | 默认边框下仍返回有效图片 |
| 提供该属性的 Windows 系统 | 原有边框策略和用户授权语义不变 |
| 资源管理器 / 微信主窗口 / 微信小程序 | 分别验证图像内容；不只检查调用未抛异常 |
| 左竖屏 + 右 4K、不同缩放比例 | 图像尺寸、窗口位置和点击坐标一致 |
| 目标遮挡 / 最小化 / 锁屏 / 远程会话 | 明确行为与失败原因，禁止返回旧图当作新图 |

**完成条件：**本机通过官方 `@oai/sky` 连续获取新的窗口截图，并在目标微信 / 小程序场景验证内容和后续操作坐标。仅有本项目的 GDI 成功不满足此条件。

当前依赖：官方后端源码 / 兼容构建或已发布修复版本。项目内无法通过增加 Python 包来完成这一步。

### 新增：捕获帧超时的独立诊断（待开展）

在再次部署补丁前，需要用独立、可编译的 WGC 最小示例分别测试窗口捕获和显示器捕获，记录设备创建、帧事件订阅、首帧时间、适配器与输出关系。这样才能区分当前助手的捕获实现、桌面会话及显示驱动 / 系统能力问题。

本轮已经使用新辅助进程在左屏单独复测，仍发生首帧超时，排除了仅由前一次工作线程卡住造成该结果的解释。尚未证明某个虚拟显示驱动就是根因，也尚未证明升级系统一定解决后续帧问题。

## 阶段 3：操作系统迁移备选方案（尚未实施）

若无法获得支持旧系统的后端，可评估迁移至实际提供所需接口且受支持的 Windows 版本，例如经兼容性确认的 Windows 11。

执行前需完成：

1. 核对硬件、系统版本与许可、微信及现有工程软件兼容性。
2. 准备完整系统备份和恢复介质，记录显示器布局与远程显示驱动版本。
3. 确认安装介质、版本、维护时段和回退方式，形成可审阅的迁移清单。
4. 升级后先运行能力探测，再做官方截图验收。

本次没有执行系统升级、重启或驱动替换；它们会中断现有工作，需要在上述清单齐备后单独安排。不能将“系统版本号看起来更高”当成验证通过。

## 阶段 4：命令入口和系统维护（已适配入口，CET 根因待处理）

- 当前项目诊断使用 `cmd.exe` → 系统 Windows PowerShell 5.1，Python 工具直接运行。
- `-ExecutionPolicy Bypass` 仅作为本次诊断进程参数，不修改持久执行策略；只运行仓库内已审阅的脚本。
- 后续根据机器实际补丁与维护历史，核对捆绑 .NET 所需条件；必要时在独立目录使用兼容的 PowerShell 版本，不覆盖 Codex 自动管理的运行时。
- 系统维护后分别复测 `pwsh.exe --version` 和 WGC；不要合并它们的验收结果。

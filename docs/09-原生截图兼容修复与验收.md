# 09 原生截图兼容修复与验收

日期：2026-09-21。**本机官方 `sky.get_window_state` 已通过本地兼容层恢复资源管理器截图，截图与可访问性文字可同时返回。当前保留的是本地修改版本，尚非厂商发布的正式修复。**

## 实际根因与对照证据

原先存在两个先后发生的阻断点：

1. 当前系统没有 `GraphicsCaptureSession.IsBorderRequired`，后端尝试关闭捕获边框时先报 `0x80004002`。
2. 跳过边框设置后，在 `FrameArrived` 回调内部同步等待 `SoftwareBitmap.CreateCopyFromSurfaceAsync` 会超时。这个超时不能解释成“系统没有产生捕获帧”。

本轮用独立 C++ 程序验证了第二点，具体结果如下。统计来自本机最新一轮对照，耗时会随负载变化。

| 测试 | 结果 |
| --- | --- |
| 主屏基础 WGC 帧捕获 | 172 ms 收到有效帧，3840×2160 |
| 回调内等待异步表面转换 | 已收到帧，等待转换 2 秒超时 |
| 独立 MTA 线程执行同一异步转换 | 成功，约 31 ms，BGRA8 / Straight alpha |
| 回调内经兼容层同步读取 WGC 纹理 | 成功，约 31 ms，3840×2160 |
| 左侧竖屏经兼容层捕获 | 成功，约 15 ms，1440×2560 |
| WARP 软件设备经兼容层捕获 | 成功，约 62 ms，3840×2160 |
| 指定资源管理器窗口经兼容层捕获 | 成功，1391×1069 |

正常转换路径还验证了像素范围和真实位图尺寸。这里的原始窗口尺寸与官方工具输出的缩放图尺寸不同，不能直接把二者当作同一坐标系。

OpenAI 仓库中已有另一位用户报告同类回调等待问题；该报告用于确定测试方向，本机结论以本轮独立对照和原生接口验收为依据。[问题报告 #35446](https://github.com/openai/codex/issues/35446)。Microsoft 文档说明 `CreateFreeThreaded` 的帧事件在内部工作线程上触发。[CreateFreeThreaded 文档](https://learn.microsoft.com/en-us/uwp/api/windows.graphics.capture.direct3d11captureframepool.createfreethreaded)

## 本地兼容层怎样工作

本轮保留 WGC 获取图像、官方 JavaScript 接口、应用授权、窗口选择、裁剪及 JPEG 编码流程，针对当前辅助程序做两处适配：

- 跳过可选的关闭边框操作，保持系统默认捕获边框。
- 将 `SoftwareBitmap` 的表面复制改为 D3D11 staging texture 读取，再创建真实的 WinRT 位图。返回已完成的 `IAsyncOperation`，避免在帧回调中等待原本会卡住的异步转换。

初版兼容层已推进到 JPEG 编码阶段，但使用 Premultiplied alpha 时被原生编码器拒绝。对照系统正常异步转换的结果，确认本机默认结果是 **BGRA8 / Straight alpha**。修正后通过了官方截图验收。初版安装已完整回退。

构建脚本仅接受已检查的原文件 SHA-256，保留原有导入表并添加兼容 DLL 的导入；对 WinRT 激活入口的局部转接仅替换 `SoftwareBitmap` 静态接口，其余激活请求交回系统。没有更改应用授权或操作系统信任策略。

**当前兼容程序的 Authenticode 状态为 `NotSigned`，不再具有原文件的有效厂商签名。** 原始签名有效的程序有完整备份，已验证可以恢复。补丁只适用于上述版本，不能给升级后的其他哈希强行应用。

## 原生接口验收

验证链路为：标准 MCP stdio → 已安装的 `node_repl` 的 `js` 工具 → 官方 `@oai/sky` → 应用管理的原生管道 → 当前辅助程序。没有直接构造原生辅助程序私有协议请求。

本轮用户明确允许对资源管理器进行读取和截图诊断；应用授权由同一链路正常请求和处理。

- `sky.list_windows()` 成功，按实际返回对象选择唯一资源管理器窗口。
- `sky.get_window_state({ include_screenshot: true })` 返回真实 JPEG 和官方截图 ID；已目视核对 1100×849 的窗口图，文字、图标和文件列表正常。
- 连续三次 `include_screenshot: true, include_text: true` 均成功。
- 完整回退后，原哈希与 `Valid` 签名恢复；重新安装后，由应用启动新的辅助进程，再连续三次图文快照仍全部成功。
- 最后一组三次快照各包含 5 张工具输出图，文本树长度为 7637、7688、7688。输出数量可能随窗口附属界面变化。

结构化证据见 [本轮验收记录](evidence/2026-09-21-wgc-readback.json)。图片、完整 MCP 输出、构建产物和厂商备份留在 Git 忽略的 `artifacts/` 中。

尚未验收微信小程序订单页、HDR、截图坐标点击以及完整 Codex 应用更新或重启。本轮确认的是当前本机原生截图和文字读取链路恢复。

## 检查当前安装与回退

在项目目录的命令提示符中检查：

```bat
C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe -NoLogo -NoProfile -NonInteractive -ExecutionPolicy Bypass -File scripts\install-wgc-readback.ps1 -Mode Status
```

当前应显示 `IsReadbackCompat: true`、`CompanionMatches: true`、`BackupExists: true`。`Signature: NotSigned` 是这个本地修改版本的实际状态。

完整恢复厂商原程序：

```bat
C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe -NoLogo -NoProfile -NonInteractive -ExecutionPolicy Bypass -File scripts\install-wgc-readback.ps1 -Mode Rollback
```

脚本只停止匹配的原生辅助进程，等待其光标管理子进程自行退出，然后恢复原程序并删除本次新增的兼容 DLL。备份位于 `artifacts/backups/wgc-readback-validated-20260921/`；保留整个目录才能使用默认回退命令。回退后会恢复原版在本机上的截图兼容问题。
